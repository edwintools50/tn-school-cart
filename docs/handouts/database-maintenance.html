1 · How the pieces fit together

TN School Cart is a single Next.js application. It doesn't have a separate backend server — pages and Server Actions talk to the database directly through Prisma, an ORM that turns the schema in prisma/schema.prisma into type-safe database calls.

The database itself is PostgreSQL, hosted on Neon (a serverless Postgres provider). Neon isn't baked into the code — it's just "a Postgres server," reached through a connection string stored in the DATABASE_URL environment variable. The app connects to it via @prisma/adapter-pg, defined in src/lib/db.ts.

2 · The data model

Eight models. Every user — principal, supplier, worker, or admin — is a single User row distinguished by a role.

User

role (PRINCIPAL / SUPPLIER / WORKER / ADMIN) · status (PENDING / APPROVED / REJECTED / SUSPENDED) · contact & role-specific fields (schoolName/district for principals, businessName/serviceArea for suppliers & workers)

Product → CartItem → Order → OrderItem

A Product belongs to a supplier User and has a moderation status. Buyers accumulate CartItems, and checkout turns them into one Order containing several OrderItems — each item keeps its own status (Placed/Confirmed/Shipped/Delivered/Cancelled) and a snapshot of the price/title at the time of order, so later edits to the product don't rewrite order history.

GigService → GigRequest → GigOffer

A GigService is a worker's listing (moderated, same as products). A GigRequest is a job a principal posts; workers respond with GigOffers. Accepting an offer sets the request's status to ASSIGNED and the offer's status to ACCEPTED, auto-rejecting the rest.

Category enums

ProductCategory and GigCategory are plain string enums in the schema — Postgres stores them as text, so adding a new one is a schema edit, not a data migration (see §6).

3 · Where the database lives

  1. Log in at console.neon.tech with the account that created the project.
  2. Open the tn-school-cart project. The dashboard shows compute usage, storage, and active connections.
  3. Connection Details is where the connection string lives — this is the value stored as DATABASE_URL in Vercel's environment variables. Treat it like a password: whoever has it has full read/write access to every school, order, and account on the platform.

4 · Everyday inspection

Two ways to look at the data without writing raw SQL:

Prisma Studio (recommended for quick lookups)

# from the project folder, with DATABASE_URL set in .env
npx prisma studio

Opens a local browser UI where you can browse, filter, and edit every table with a spreadsheet-like interface — the fastest way to check "did this order actually get created?" or manually fix a single row.

Neon's SQL editor

Inside the Neon dashboard, the SQL Editor tab lets you run raw queries directly against production — useful for aggregate questions ("how many orders this week?") that Prisma Studio isn't built for.

5 · Making schema changes safely

Never hand-edit tables in Neon to add a column — always go through Prisma's migration system so the schema file, the migration history, and the actual database stay in sync.

  1. Edit prisma/schema.prisma with the change you want.
  2. Run npx prisma migrate dev --name describe_your_change locally. This creates a new file under prisma/migrations/, applies it to your local/dev database, and regenerates the Prisma client.
  3. Test the change locally (npm run dev).
  4. Commit the new migration folder along with your code changes, and push.
  5. Apply the same migration to production: DATABASE_URL="<production connection string>" npx prisma migrate deploy. This runs any migrations Neon hasn't seen yet — it does not touch data outside what the migration specifies.
  6. Vercel redeploys automatically on push; its build step runs prisma generate (via the postinstall script) so the deployed app matches the new schema.
Order matters

Run migrate deploy against production before or immediately after the code that depends on it goes live — if the deployed code expects a column that doesn't exist in the production database yet, requests touching that table will error.

6 · Worked example: adding a new marketplace category

This is the concrete version of what the Admin Handbook refers suppliers/workers to you for.

  1. In prisma/schema.prisma, add the new value inside enum ProductCategory or enum GigCategory.
  2. Run npx prisma migrate dev --name add_category_x (for Postgres text-enum columns this is usually a no-op at the SQL level, but keeps history consistent).
  3. Add a human-readable label for it in src/lib/constants.ts — PRODUCT_CATEGORY_LABELS or GIG_CATEGORY_LABELS. Every dropdown and filter on the site reads from this file, so this one line is all the UI needs.
  4. Commit, push, and deploy as in §5.

7 · Backups & disaster recovery

Neon keeps a rolling history of your database automatically (point-in-time restore), letting you branch or roll back to an earlier moment from the Neon dashboard — the retention window depends on your Neon plan, so check Settings → Backup/Restore in the Neon console for exactly how far back you can go.

For an extra manual snapshot before a risky change (a big migration, a bulk data fix), take one yourself:

# requires the postgres client tools (pg_dump) installed locally
pg_dump "<production DATABASE_URL>" -f backup-$(date +%Y%m%d).sql

8 · Connection pooling — action needed

Flag for follow-up

The DATABASE_URL currently in use points at Neon's direct connection endpoint (no -pooler in the hostname). Vercel runs the app as serverless functions, and under real traffic each concurrent request can open its own database connection — Postgres (and Neon's free-tier direct endpoint) has a limited connection ceiling, so this will eventually cause connection errors under load, even though it works fine at low/demo traffic today.

Fix: in the Neon dashboard, under Connection Details, toggle Pooled connection — it gives you a connection string with -pooler in the hostname, backed by PgBouncer. Swap that in as the DATABASE_URL in Vercel's environment variables (no code changes needed) and redeploy. Do this before the site has meaningful real-world order volume.

9 · Monitoring

  • Neon dashboard — compute hours used, storage, and active connections. Free-tier compute auto-suspends after inactivity and cold-starts on the next request (this is why the very first request after idle time can feel slow).
  • Vercel dashboard → your project → Logs — every server error (including database errors) from production shows up here in real time, filterable by route.

10 · Environment variables & secrets

VariablePurposeRotating it
DATABASE_URLPostgres connection stringReset the password in Neon → update in Vercel env vars → redeploy
SESSION_SECRETSigns login session cookiesChanging it instantly logs every user out (all existing session tokens become invalid) — safe to do, just expect a wave of re-logins

Both live only in Vercel's Project Settings → Environment Variables and in each developer's local .env file (which is git-ignored) — never in code or committed files.

11 · Seeding & demo data

npm run seed runs prisma/seed.ts, which upserts (by email) a set of demo accounts, products, and services. It's safe to re-run against a fresh or staging database — but avoid running it against production once real schools and vendors have signed up, since its purpose is demo/testing data, not something a live marketplace needs re-added.

12 · Before going fully live

  • Switch DATABASE_URL to Neon's pooled connection string (§8).
  • Change the seeded admin password (admin@tnschoolcart.in) away from the demo default — it's written in this project's README and known to anyone who's read it.
  • Decide whether to keep or remove the seeded demo accounts/listings once real suppliers and workers are onboarding.
  • Confirm SESSION_SECRET in Vercel is the production value generated for this deployment, not the placeholder committed in the repo's .env for local dev.
  • Set a reminder to check Neon's plan limits (storage, compute hours) as real usage grows.
